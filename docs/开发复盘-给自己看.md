## 2026-10-14 收尾更新：先读这一节

**当前结论：本地演示版基本形成闭环，可以冻结为求职项目第一版；不是生产级产品，更没有公网上线。** 下文一至八节保留旧V1时期的历史说明与计划，其中“尚未Docker实跑”“当前只有30题”“准备实现全文对照”等描述已过时，以本节为准。历史数字不代表新版准确率。

### 1. 当前版本在哪里，完成了什么

- 主项目保留旧V1；新版位于相邻 `Research_Copilot_ablation` 工作树，分支 `experiment/ablation-20261005`。已推送收尾提交 `ccb3124`；本节更新不代表新版已合并main。冻结V1仍用于回退和对照。
- 旧 `/chat` 是预检索问答；新版 `/research` 是自适应论文阅读入口，管理员 `/admin/research` 查看Trace。不是简单把旧网页改名成Agent。
- 新版支持本机PDF导入、通用知识、全文阅读、RAG片段检索以及自动选择；策略和讲解深度是两回事。auto目前依靠问题规则与输入预算，不保证选对。
- RAG工作流是单Agent的受控Python编排：用户问题→模型规划1–2子问题→每题检索→模型判断缺口/提议动作→程序检查来源、白名单和预算→可选补查或展开→最终有限回答→私有Trace。模型可以提出聚焦的新查询，但不能无限调用工具。旧V1仍有LangGraph与SQLite检查点，不应把新版Python状态编排全部称为LangGraph实现。
- 默认保留直接全文讲解；结构化资料表仍是实验开关，未证明值得作为默认。没有自评分触发循环重写。Docker验收明确关闭辅助审阅；其他入口的默认设置需看其配置，不能说全局都关闭。
- 稳定性治理：统一模型配置、DeepSeek输出参数适配、输出6400 Token上限、截断后完整段落恢复、单条异常不丢整份、评估子问题隔离、停止补查仍继续写作、refuted_premise区分错误前提与内部证据冲突。程序校验来源身份不等于语义正确。
- 2026-10-13收尾源代码210项离线回归通过；2026-10-14前端契约测试加入后212项通过，外网被测试运行器禁止。这个数字证明行为契约与回归，不证明论文答案准确率。
- 2026-10-14 Docker验收项目使用独立镜像/项目名、仅绑定127.0.0.1:8020。旧V1容器与主项目数据不动。研究/管理员页面HTTP 200；真实Informer问答跑通；force-recreate后用户确认论文列表、管理员记录仍存在，Trace文件也在宿主机。未做新PDF容器导入验收、长时间并发/负载/故障演练，不夸称全面黑盒验收。

技术栈：Python、FastAPI/Uvicorn、LangChain/旧路径LangGraph、ChromaDB/HNSW、PyMuPDF、SQLite、DeepSeek生成接口、阿里云嵌入接口、旧OSS/STS上传、原生HTML/CSS/JS、Docker Compose、GitHub Actions离线检查。没有实现BM25/Cross-Encoder/GraphRAG/多Agent，不把未来技术写成当前栈。

### 2. 为什么折腾这些：我自己提出的问题

| 我的疑问 | 形成的取舍或结论 |
|---|---|
| GPT已经能读论文，RAG还有什么价值？ | 不以“新技术”作理由；全文适合整体理解，RAG适合限制输入成本与局部查证。两者都设预算，靠对照决定，不预设RAG更好。 |
| 旧A1/A2/B/C路由误判会不会把后面全部带偏？ | 会。固定章节限制有成本价值也有质量风险；新版不把旧四类路由当硬性研究流程。 |
| Token不爆炸与Agent自主决策怎么兼顾？ | 允许规划、改写检索和展开，但执行框架限制工具、次数、时间、证据和输出；自主不是无上限。 |
| 没读论文，如何做人工盲审？ | 不假装专家gold；AI起草参考、LLM裁判只是辅助。选本人读过的论文做有限事实抽查，未知不填成对/错。 |
| partial是不是一定回答差？ | 不是。模型可能把额外公式或未要求的深度当缺口；过程状态与答案质量分开统计。 |

| 没检索到是不是论文没写？ | 绝对不是。统一边界标题，并明确当前证据未覆盖；正文模型仍可能越界，属于未解决的语义风险。 |
| 通用知识能否协助查证？ | 能提出检索假设、教学解释和证据推断，但不伪装成作者原文。一致不是独立证实，不一致是核查信号，不直接判错。 |

| 能否主聊天＋侧边概念追问？ | 有个人使用价值，列为未来交互方案；未实现，不为简历收尾扩展。 |

### 4. Trace和Eval怎么讲，而不是只报数字

Trace保留已见证据→模型判断→门禁放行/拒绝→实际动作→停止原因，以及调用、Token、时间。模型负责语义判断，程序负责身份/结构/预算约束，人工抽查效果。旧request_metrics是无内容遥测；新版私有Trace包含问题、片段、答案和原输出，两者不能都称“无内容日志”。Trace不上公开Git。

Eval分层：离线单测证明预算、隔离和降级分支；真实小样本证明接口/流程能运行；人工检查核心事实与切题；过程指标用于定位原因。没有专家金标准、没有独立保留集上证明优越、没有全回答引用准确率。LLM-as-a-Judge工具/裁判实验不当作人工真值，也没有自评分阈值触发循环重写。

八题三组开发验收（非holdout）：旧V1受控单轮适配器、auto、直接全文。第一批与修复后的第二批代码不同，不能直接当同版本统一测试集。两个批次各12槽位，总24槽位：21份实际有正文、2份停止（第一批条目长度校验、第二批评估门禁）、1份综述全文不适用。该“有正文”不是准确率；不把修复回放当新模型成功。

用户评价：全文通常更详细，但有因果/边界断言问题；旧V1有时更直接，但大量引用、缺证据和过度拘泥字面影响体验；auto能规划补查，却仍召回遗漏或误判充分性，没有一致优于其他组。用户愿意接受非生产级第一版，说明可读性基本可用，不证明零幻觉。

真实Docker单题729191ef-1c0e-46d1-9351-77a7e600fa3a：refuted_premise生效，stop后最终回答，3次模型、2次检索，12.65秒，辅助审阅关闭。带近期历史，不是空历史对照。答案核心结论对，但把当前片段未覆盖写成论文没给X0填充值、mask因果解释过强等问题仍在。此例证明工作流修复真实生效，不证明语义缺陷已修复。

### 7. TimesFM容器最小验收与我的下一轮思考（2026-10-14）

用户完成2023_TimesFM.pdf的本机导入，产生新论文会话6232f9d3-3747-4a68-b125-a33b420383c7；不是直接复用原有论文记录。容器内整体讲解请求0b960c30-acab-4fc8-9fc9-ded73b1cdcd9和局部patch/residual block追问c40dd87c-21f1-400e-bda1-c24a32267789均实际进入RAG规划、检索、补查和最终回答，3次模型调用、3次检索，状态insufficient，正文保留并披露缺口。用户评价“回答大半且基本正确，有缺失”，不能把它转换成准确率。随后同一局部问题的深入分析请求6053ccf8-6838-44ef-a0c0-56d36b5ed0a4状态ok_with_limits；带前两轮历史且深度不同，不能用状态差别宣称召回或质量提升。

由此最小功能链可记录为导入、新论文选中、整体讲解、局部追问和Trace留存跑通；语义充分性并未过关。用户指出参数量等信息在论文有出处，却未进入回答。该疑点要进一步拆成“解析源是否有→是否进入初始/补查候选→排序筛选是否保留→打包截断是否保留→模型是否读对”，不凭最终答案缺失就武断判断丢在哪一层。本轮只记录，不改变召回、预算或提示词。

我的后续思路一：先利用大模型通用知识理解任务和拆分问题，生成待验证术语/章节假设，再根据当前PDF检索，可在既定预算内多轮；把模型知识与论文证据的相符/不符当作核查信号。相符不等于独立证明，模型可能记忆同一论文；不相符也可能是版本、条件、语境或模型知识过时。通用概念解释可以作为教学背景，参数量、实验数字、作者结论、局限和继承关系仍要当前原文支持。

我的后续思路二：优先提高候选召回覆盖及证据选择质量。可另做BM25＋Dense融合候选与Cross-Encoder重排小对照；重排不能修复没有进入候选的段落。保留逐阶段候选ID、选中ID、文本范围和拒绝原因，才能知道是候选遗漏、选择淘汰还是截断。建立少量真实相关块人工标注，不再把关键词命中当专家语义正确率。

本轮决策：接受有明确边界的本地第一版，停止质量调优，保存并合并源码；未来升级独立立项，不为收尾继续累加多轮知识验证、混合检索或多Agent。

## 一、项目是什么（一句话）

单篇论文的**证据绑定**阅读助手：上传 PDF → 解析章节和页码 → 向量检索 → 生成前注入"有预算"的论文证据 → 输出带【来源章节 + PDF 页码 + 原文引用】的结构化摘要和多轮问答。

核心不是"又一个论文聊天机器人"，而是让**论文事实、模型自身知识、我的推断**三者有清晰边界，降低幻觉和"历史倒置"（把论文之后才出现的技术说成论文内容）。

---

## 二、为什么做这个（起源）

最早想做的是 **AI CodeReview Agent**，放弃了，理由就两条（原始论证见本地 `归档/起源-构思.md`）：

1. **价值站不住**：把代码丢给通用大模型也能出一份审查报告，自研系统的增量价值说不清。
2. **成本不成立**：真实项目代码量巨大，全量塞进 LLM 的 token 消耗不可控，架构上没法自洽。

转做**单篇论文阅读助手**后这两条都不成立：论文是有限长度的自包含文本，而"这句话到底出自论文哪一页"是通用聊天机器人给不了的——**可核验**成了真正的差异化。

## 四、已实现功能 & 用到的技术

### 1. 论文上传
- 浏览器通过**阿里云 OSS + STS 临时凭证前端直传**，后端只负责签发临时 token（`oss_sts.py`、`app.py` 的 `/oss/token`）。
- 技术点：STS 最小授权、前端直传（后端不扛文件流量）。
- 取舍：PDF 从不进 LLM，OSS 并不省 token、还多一跳；保留它主要为 V2 多论文库持久化原文铺路。

### 2. PDF 解析与结构化（`paper_parser.py`）
- PyMuPDF（fitz）逐页提取文本。
- **去页眉页脚噪声**：识别跨页重复的作者名、页码、期刊标记并剔除（有单元测试）。
- **章节识别**：匹配常见英文学术标题（Abstract / Method / Experiment / Conclusion 等）。
- **章节内切块**，每个 chunk 携带 `section`、`page_start`、`page_end`、`_order`。
- 技术点：物理 PDF 页码全程可追溯。

### 3. 向量存储与检索（`rag_store.py`）
- ChromaDB `PersistentClient`，每个会话一个集合 `paper_<thread_id>`；默认 **L2** 距离、HNSW。
- Embedding：DashScope，**按 20 条分批**（单批上限），按返回 `index` 排序对齐，失败透出 HTTP 响应体。
- **MMR（最大边际相关）**：召回池 20，λ=0.7，在"相关性"和"去重/多样性"间折中；自带向量归一化与余弦相似度。
- **会话级 chunk 记忆**（`agent_setup.py:17,30-36`）：`_seen_chunks` 记录本会话已发给模型的 chunk id，检索时用 `exclude_ids` 排除；每轮新请求开始时 `reset_retrieval_memory()` 清零（`agent_setup.py:50-53`），保证新一轮能从头检索。
- **递归保险丝** `recursion_limit = 15`（`app.py:170`）：防止 Agent 工具死循环。
- `list_chunks(thread_id)`：按 (页码, 顺序) 返回全部块，供结构性兜底。
- 重新上传时 `delete_collection`，保证"一会话一篇论文"。

### 4. 查询路由（`query_router.py`）
- 生成前一次**廉价 LLM 调用**（max_tokens≈50, temperature=0）把问题分四类：
  - **A1 论文事实** → 检索
  - **A2 论文局限/改进** → 检索 limitation / future work
  - **B 领域知识**（与论文无关）→ **不检索**，用模型自身知识
  - **C 创新推理** → 检索论文细节 + 结合领域知识
- 失败时**保守回退 A1**（宁可多检索，不漏检索）。
- 这套标签同时用于 prompt 的来源标注。

### 5. 证据构建与注入（`app.py`、`agent_setup.py`、`prompts.py`）
- **不给模型注册检索工具**。检索在 Python 侧、生成之前完成，证据通过 `@dynamic_prompt` 运行时上下文**只注入当前这一轮的系统提示词**。
- 证据预算：单块最多 600 字符，每次最多 8 块、总计 6000 字符；最多 6 块来自语义检索，其余用于章节覆盖。
- **结构性兜底**：语义检索不足时（尤其非标准结构的综述），用 `list_chunks` 按章节优先级补齐，优先选语义相关块，再按页序；排除 references/appendix 和过短块。
- **证据铁律**：检索文本是唯一事实来源；一级事实（贡献/实验数据/结论）必须附【来源】+【原文引用】；论文没写必须说"论文中未找到"。
- **三类内容分层**：A1 论文明确说 / A2 从设计推导 / B 领域背景（标"非论文内容"）/ C 我的推断，严禁伪装。

### 6. 对话持久化与覆盖语义
- LangGraph（`create_agent`）+ `SqliteSaver` 检查点，SQLite 存会话元数据与检查点（`database.py`、`agent_setup.py`）。
- 每轮请求前清理历史里的工具相关消息（见难题 1）。
- 同一会话上传新 PDF：**新论文解析成功后，同时清空旧检查点历史 + 删除旧向量集合**。

### 7. 评测与可观测（V1.1）
- `benchmark/`：路由准确率 + 检索命中率（确定性、机器判），人工评引用/接地/幻觉（人判）。
- `request_metrics` 表：只存**非内容**遥测——请求类型、路由、证据块数/字符数、各阶段耗时（download/parse/index/routing/retrieval/generation/total）、输出字符、provider token；**不存**用户问题、证据、答案；最多保留 1 万行。
- `metrics_report.py` 输出成功率、各耗时 mean/p50/p95、token 统计。
- `tests/test_core.py`：3 个离线单测（噪声与页码、结构性兜底排序、遥测隐私边界）。

### 8. 交付准备（已配置、未实操）
- `Dockerfile`、`compose.yaml`、`.dockerignore`、GitHub Actions（装依赖 + 语法检查 + 离线单测）。真实模型/OSS 调用不进 CI。

## 五、踩过的难题（按解决顺序）

1. **证据跨轮累积（token 爆炸主因）**
   早期 Agent 工具返回的大段论文文本进入 checkpoint，追问越多重发越多、token 线性增长。
   解法：后端预检索 + 证据只注入当前动态提示词（不产生 ToolMessage），并清掉历史中的 ToolMessage 与带 tool_calls 的 AIMessage。多轮发送量从"线性增长"变为"基本恒定"。

2. **覆盖上传串论文**
   只删向量不删对话时，旧论文的文字回答仍影响新论文。
   解法：新 PDF 解析成功后，同时清空该 thread 检查点历史和旧向量集合。

3. **GPT 改代码导致乱码 + 语法错误**
   外部工具改写后出现 UTF-8 乱码、字符串未闭合、注释吞掉 `if` 等。
   解法：整体重写 `app.py` / `agent_setup.py` / `prompts.py`，统一正确的中文编码。教训：外部大改后要先跑编译和测试再继续。

4. **跨线程 `sqlite3.ProgrammingError`**
   根因：LangGraph 从**自己的后台线程池**写检查点，不是 SSE worker 线程。
   解法：单连接 + `check_same_thread=False`（SqliteSaver 每个操作都用内部 `self.lock` 包裹，因此安全）+ WAL 模式 + `busy_timeout=10000`。用 4×4 并发验证通过。

5. **上传后"显示输出中"但没有内容（空流）**
   根因：omni-flash 默认开 thinking + 长 prompt，超过当时 30s timeout，正文还没开始就被切断，推理 delta 变成空 chunk。
   解法：`extra_body={"enable_thinking": False}`、timeout=120、max_tokens=8192。验证可正常输出 3000+ 字摘要。

6. **非标准结构综述"证据不足"**
   固定的摘要查询命中不到非典型章节，证据块太少。
   解法：`list_chunks` + 结构性兜底，按章节优先级选块、过滤参考文献和过短块。验证可输出 3800+ 字摘要。

7. **页眉页脚噪声**
   跨页重复的作者名/页码/期刊标记污染正文。
   解法：按重复模式识别剔除，并保留 chunk 的页码正确性（有单测）。

8. **embedding 超批直接 400**
   论文切成几十个 chunk 一次性提交，超过 DashScope **单批 20 条**上限直接报错。
   解法：按 20 条分批请求，按返回 `index` 排序对齐，失败时把 HTTP 响应体透出来（`rag_store.py:20-38`）。

9. **Docker 在本机起不来**
   `docker compose up` 报 desktop-linux 引擎管道不存在。根因是**硬件虚拟化未开启**（`VirtualizationFirmwareEnabled=False`）。
   解法：进 UEFI/BIOS 开 Intel VT-x → 任务管理器确认"虚拟化：已启用" → 更新 WSL → 重启 Docker Desktop。**这一步至今没做，Docker 配置仍是"写了但没实跑"**。

10. **依赖清单缺口 `langchain-openai`**
    本机装了不代表干净容器里有。已补 `langchain-openai==1.3.3`，修的是清单，不等于镜像构建已验证。

11. **Windows 下 Chroma 文件占用**
    清理临时快照时报文件被占用。解法：改为在私有输出目录保留快照后重新生成。

## 六、当下仍存在的真实问题（⚠️ 不粉饰，留待优化）

### P0：检索"知道去哪个章节，却挑不中关键实体块"
在自建 30 题评测集上（`benchmark/reports/v2.json`），路由 100%，但检索命中率 91.7%，挂红的两题是同一类问题：

| 题 | 关键实体 | 全文出现次数 | 现象 |
|---|---|---|---|
| s-a1-04（问实验数据集） | `Pile` | 10 次 | 章节找对（experiment），但含 Pile 的块没进证据 |
| a-c-01（问可解释性新想法） | `Kakeya` | 19 次 | 章节找对（method），但含 Kakeya 的块落选 |

更早一轮还观察到 `attention`（211 次）、`structured matrices`（19 次）同样落选过。
**根因判断**：纯向量语义检索按"意思相近"选块，而问题里根本没出现 Pile / Kakeya 这些专名，导致专门讲它的句子语义上不够"近"。这是产品真问题，**改标准答案救不回来，重跑仍会挂红**。
**候选解法**（V2 评估，不要一次全上）：
- 检索后加一轮**实体感知/关键词重排**；
- 或在检索前从问题/章节抽取实体做**混合检索（向量 + 关键词 BM25）**；
- 或扩大召回池后加 **cross-encoder 精排**。
每种都要在同一评测集上做前后对照，用命中率说话。

### 其它已知问题
- **无 cross-encoder 精排**：复杂问题召回相关性没有二次打分。
- **度量不一致**：Chroma 集合用默认 L2，而 MMR 内部自己做余弦；严格做法是建集合时显式声明 `hnsw:space: cosine`。
- **物理页码偏移**：记录的是 PDF 物理页序，带封面/目录的期刊论文，正文印刷页码会有偏移。
- **路由多一跳 LLM**：每个问题多一次网络往返和失败点；若错分成 B（该查却没查）会降低质量，目前靠"失败回退 A1"兜底。
- **长程记忆依赖重检索**：很早以前问过的细节，下一轮要重新检索才想得起；连贯性靠保留的问答文字维持，不是完美方案。
- **OSS 必要性存疑**：当前多一跳延迟，价值要等 V2 才兑现。
- **评测规模偏小**：仅 3 篇论文、30 题，数字有参考价值但代表性有限，面试要能讲清方法而非只报数字。

### 评测口径：历史数字怎么用（⚠️ 别把过程指标当结论）

| 报告 | 路由正确 | 原报告检索命中 | 固定"应检索题"分母后的命中 |
|---|---:|---:|---:|
| `benchmark/reports/v1.json` | 26/30 = 86.7% | 14/20 = 70.0% | **14/24 = 58.3%** |
| `benchmark/reports/v2.json` | 30/30 = 100% | 22/24 = 91.7% | 22/24 = 91.7% |

- v1/v2 只是**历史报告文件名，不代表做过产品 V2**。
- v1 第一轮有 4 道本应查论文的题没留下检索结果。只看"实际检索的 20 题"会把它们移出分母，**等于奖励漏查**；按预先标好的 24 道应检索题算才是诚实的。
- 路由 30/30 的 Wilson 95% 区间约 **88.6%–100%**；检索 22/24 约 **74.2%–97.7%**。样本小，区间很宽，别只报那个漂亮百分比。
- 遥测库里目前只有 **1 条**请求记录，**不能据此报 p95、并发能力或成本节省**。
- 历史报告没记代码/语料/模型哈希，**不能包装成严格控制变量的因果实验**，更谈不上"已证明比朴素基线提升 33 个点"。

### 最新一轮：72 题双变体开发评测

已完成 72 题双变体（朴素基线 vs 当前 agent）开发评测，结论是 **V1 路由在 A2、C 两类题上的命中率低于基线**，下一步要**盲审**查原因。
另需注意：现有 72 题里**没有 B 类（通用知识）题**，因此"不该检索就不检索"能省多少 token **根本测不出来**。

### Judge（LLM 裁判）的已知缺陷

- 旧 Judge 用统一候选片段（约 1200 字）核验全部答案，已出现过把上下文中真实存在的 `Traffic x22` 误判为幻觉的案例。
- 新脚本 `judge_evidence_v2.py` 改用每题保存的完整 evidence，指标为 **evidence_faithfulness**（对检索上下文的忠实性）、**citation_support**（对已有引用的支持）、**completeness**（对共同参考要点的覆盖）。**它不测整篇论文的事实真伪**。
- NA 规则：引文核验不通过、证据不足、缺轮次、API 出错时分数记 NA，**NA 的分母与同题配对数必须一起报告**，否则数字会失真。
- 答案文风可能泄露系统特征，**只能算尽力降偏差，不是绝对盲法**。机器判幻觉不可靠，人工评阅这步不能省。

### 部署安全清单（公网之前必须过）

1. `/oss/token`、`/history`、`/chat/{thread_id}/messages`、删除历史接口**都没有身份与资源归属验证**——只保护 token 接口远远不够。
2. STS AssumeRole **未按用户目录收窄 Policy**。
3. `/chat` 的 PDF URL 由客户端传入、服务器直接下载 → **SSRF 风险**；需限定可信 OSS 来源、大小/超时，处理重定向与内网地址。
4. **缺失限流、费用预算、并发限制**，公开接口会被持续触发模型费用。
5. 还没有服务器、域名、HTTPS 反向代理与备份恢复验证。

演示可先用"单用户 + 整站网关密码"的方案，但那**不等于多用户 SaaS**，别这么说。

## 七、可迁移的方法论（复盘沉淀）

1. 先定位成本/问题的**根因**再动手——token 爆炸主因是"检索结果跨轮重发"，不在表面限字。
2. 确定性高的事别交给 Agent 循环：摘要查哪几节是固定的，后端查好注入更快更省。
3. 大对象（可重取的论文片段）不进历史，用完即清；只保留不可复现的小对象（问答文字）。
4. 用廉价调用做路由决策：花 50 token 判断要不要花 2000 token 检索。
5. 检索要"控量 + 去重 + 保多样性"：截断、限条数、MMR。
6. 任务难度匹配模型，flash 够用就不上 plus。
7. 省钱与可信可以一起做：证据注入同时减少工具循环并强制溯源。
8. 外部大改后先编译+测试；任何"效果提升"都用同一评测集做前后对照，不凭感觉。

## 八、接下来做什么：把评测做成简历站得住的项目

当前家底：**3 篇论文 / 30 题**，路由 100%、检索命中率 91.7%。规模偏小，目标扩到 **10 篇 / 100 题**，并补齐四类指标：路由准确率（机器判）、检索命中率（机器判）、回答质量——引用/接地/幻觉（**必须人看**）、性能成本——延迟 p50/p95、成功率、token（真实使用积累）。

### 技术演进方向（调研结论，尚未开工）

完整调研见 `归档/开源科研助手调研_2026-10-02.md`。结论是**不要换壳成多 Agent、也不要直接上 GraphRAG**，最值得吸收的：

- **P0 整篇输入基线**：短论文直接全文输入做对照，先回答"RAG 到底值不值"，别默认 RAG 一定更好。（对应上面 72 题里 V1 输给基线的疑点）
- **P1 把证据变成一等数据结构**：`claim_id → answer_sentence → chunk_id → page → quote → verification_status`。页码、chunk_id 用程序确定性校验，只有"证据是否语义支持 claim"才交给 LLM。
- **P2 改 RAG 而不是换 GraphRAG**：扩大候选池 → 加 BM25/关键词召回覆盖专名和数字 → 轻量 rerank 或 query-focused contextual summary。（直接对应第六节 P0）
- **P3 接 Zotero**：引用可跳回 PDF 页码、结论可写回笔记，比"再加一个 Reviewer Agent"更能解释产品价值。
- **P4 最后再试 GraphRAG**，且只挑一个能证明价值的问题做对照，没收益就别塞进主链路。

核心心法：**retrieved ≠ verified ≠ cited**（检索到的、核验过的、最终引用的，是三种状态，别混为一谈）。
