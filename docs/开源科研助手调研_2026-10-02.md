# 开源科研助手技术路线调研

调研日期：2026-10-02

## 结论先行

当前项目不适合直接“换壳成多 Agent”或全面迁移 GraphRAG。最值得吸收的是四种设计：

1. **PaperQA2：** 先广召回，再针对当前问题生成片段摘要并用 LLM 重排，而不是只依赖一次向量 Top-K。
2. **Ai2 Scholar QA：** 先抽取原文引用，再规划结构，最后按引用写答案，把“检索片段”和“最终 claim”显式连接。
3. **STORM/GPT Researcher：** 对复杂调研先生成子问题和提纲，再并行搜索、聚合报告；适用于“写综述”，不必介入每一次单篇问答。
4. **Zotero 类项目：** 与真实文献管理工作流结合，支持精确跳回 PDF 页码，比单独做一个聊天网页更有产品辨识度。

推荐产品定位：**可核验的科研阅读工作台**。单篇短论文使用整篇上下文，长论文/多论文使用 RAG；通用知识显式切换；回答由 claim-证据核验层检查；跨论文全局问题再选择性进入 GraphRAG/综述工作流。

## 第一梯队：优先精读与复现思想

### 1. PaperQA2

- 仓库：[Future-House/paper-qa](https://github.com/Future-House/paper-qa)
- 定位：科学论文专用 Agentic RAG。
- 核心流程：LLM 生成检索词并找候选论文；向量召回片段；为每个片段生成面向当前问题的评分摘要；再用 LLM 重排摘要；最后基于最佳摘要生成带引用答案。
- 工程亮点：论文元数据感知、Crossref/Semantic Scholar/OpenAlex 元数据补全、缓存索引、迭代改写查询、LiteLLM 多模型、成本追踪。
- 对本项目最有价值：把现在的“一次召回 + MMR”升级为“候选池 + query-focused contextual summary + rerank”。这比立刻上知识图谱更直接地对应现有漏检问题。
- 注意：官方说明内部研究版本使用的工具、论文授权和开放版并不完全相同，不能只根据论文成绩推断开源版效果。

### 2. Ai2 Scholar QA

- 仓库：[allenai/ai2-scholarqa-lib](https://github.com/allenai/ai2-scholarqa-lib)
- 定位：跨多篇科学文献生成有组织、有 attribution 的长回答/综述。
- 核心流程：Semantic Scholar passage + keyword 双路检索；reranker 保留证据；抽取 exact quotes；生成报告提纲并把 quote 聚类到章节；按章节生成回答和论文对比表。
- 工程亮点：每条 claim 有证据，event trace 保存检索、重排、生成各阶段及成本；可作为 Docker Web App、异步 API 或 Python 库运行。
- 对本项目最有价值：把“引用”从答案末尾装饰改为生成前的数据结构：`quote -> section -> claim`。下一版证据核验层可以从这个最小数据模型开始。

### 3. OpenScholar

- 仓库：[AkariAsai/OpenScholar](https://github.com/AkariAsai/OpenScholar)
- 定位：大规模科学文献搜索与综合，公开 ScholarQABench。
- 核心流程：稀疏/稠密检索、cross-encoder reranker、自反馈检索、post-hoc attribution，并限制每篇论文进入上下文的片段数。
- 工程/研究亮点：不仅发布代码，还发布数据、检索库和评测；标准 RAG、reranker、自反思生成可以分层对照。
- 对本项目最有价值：实验设计方法——先固定标准 RAG，再逐项加入 reranker、feedback、citation attribution；避免同时改变多个组件后无法归因。
- 注意：其完整数据规模非常大，官方说明 45M 论文、200M+ embeddings 的本地检索需要大量内存，不适合个人项目照搬。

### 4. STORM / Co-STORM

- 仓库：[stanford-oval/storm](https://github.com/stanford-oval/storm)
- 定位：从网络调研生成带引用的长篇知识文章。
- 核心流程：预写作阶段搜集资料并生成提纲；写作阶段根据提纲和引用生成全文；通过多视角提问增加问题的广度与深度；Co-STORM 加入人机协作。
- 对本项目最有价值：将“问一篇论文”与“围绕主题形成综述”分成两个工作流。只有综述模式才启动 Planner/Researcher/Writer，单篇问答不承担多 Agent 成本。
- 注意：官方明确表示输出不能直接达到 publication-ready，仍需大量编辑。

### 5. GPT Researcher

- 仓库：[assafelovic/gpt-researcher](https://github.com/assafelovic/gpt-researcher)
- 定位：Web/本地文档 Deep Research。
- 核心架构：Planner 产生研究问题，执行 Agent 搜集信息，Publisher 聚合报告；支持本地文件、Web、MCP、流式进度、PDF/Word 导出和 tracing。
- 对本项目最有价值：任务状态、阶段进度、失败恢复、来源插件化、不同 report type，而不仅是 Agent 数量。
- 一个重要反例：其官方文档也说明复杂多 Agent 方案更昂贵、更慢、更难集成，适合实验和复杂报告；轻量调用应继续使用单 Agent/流水线。

## 第二梯队：产品体验与专项能力参考

### 6. Zotero Research Assistant / Zotero RAG 类项目

- 代表仓库：[qiobn/zotero-research-assistant](https://github.com/qiobn/zotero-research-assistant)、[aaron-freedman/zotero-rag](https://github.com/aaron-freedman/zotero-rag)、[zotero-rag/zotero-rag](https://github.com/zotero-rag/zotero-rag)
- 值得参考：文献库自动同步、语义搜索、混合检索、页码引用、点击跳回 Zotero 原始 PDF、MCP 接入、不同模型后端、本地隐私。
- 对本项目最有价值：你本人已经使用 Zotero。与 Zotero 打通会形成真实使用闭环：选中文献/集合 -> 发起问答或比较 -> 点击引用回到原页 -> 将结论写回笔记。
- 这比增加一个没有真实用户动作的“Reviewer Agent”更容易解释产品价值。

### 7. SurveyX

- 仓库：[IAAR-Shanghai/SurveyX](https://github.com/IAAR-Shanghai/SurveyX)
- 定位：基于文献生成学术综述。
- 值得参考：Preparation/Generation 两阶段、任务目录和中间产物持久化、最终 LaTeX/PDF 交付。
- 注意：开源版缺少在线论文检索、关键词扩展、双层语义过滤和多模态解析，不能把商业版功能当作开源代码能力。

### 8. Microsoft GraphRAG

- 仓库：[microsoft/graphrag](https://github.com/microsoft/graphrag)
- 定位：从非结构文本抽取实体、关系和社区结构，为局部实体问题和全局语料问题构造上下文。
- 适合的问题：跨论文方法关系、作者/模型/数据集/指标网络、研究方向的全局主题与冲突。
- 不适合直接解决的问题：单篇论文中的某个公式、参数或实验数字是否召回。
- 当前风险：官方仓库已说明项目大体进入 maintenance mode，并警告索引成本高、开箱效果需要 prompt tuning。它适合作为后续实验支线，不应成为下一版主干依赖。

### 9. LangChain Open Deep Research

- 仓库：[langchain-ai/open_deep_research](https://github.com/langchain-ai/open_deep_research)
- 值得参考：LangGraph 状态、结构化 research task、并行子研究和可配置模型/搜索工具。
- 风险：该官方仓库目前标为 archived。适合读其状态设计，不适合把它作为长期核心依赖。

## 新近个人项目中值得借鉴、但不要直接当成熟基准的思想

- **逐条 claim 核验：** 有项目把报告拆成原子 claim，并用全新上下文单独验证 claim 与来源文本，避免生成模型在原对话里“自己给自己打分”。这是当前裁判失败后很值得采纳的架构思想。
- **证据图而非概念知识图：** `Report -> Claim -> Evidence -> Source` 的可审计关系图，对当前项目比一开始就抽取所有领域实体更有用。
- **确定性检查与 LLM 检查分层：** DOI/标题/页码/引用 ID 是否存在优先用程序校验；只有“证据是否语义支持 claim”才调用模型。
- **Retrieved != verified != cited：** 检索到的片段、核验过的证据、最终答案采用的引用应是三种不同状态。

这些项目中有些很新、使用者少或主要由 README 描述，适合作为设计灵感，不能作为性能或成熟度证据。

## 小红书检索说明

公开搜索没有返回可稳定访问、可核对代码或技术细节的小红书帖子。小红书内容普遍依赖登录和客户端，搜索摘要也不适合作为架构证据，因此本轮没有用帖子中的宣传数字。产品灵感已经由公开可复核的开源仓库覆盖；后续若你给我具体帖子链接，可以逐条拆解其功能是否真的有代码支撑。

## 对当前项目的可执行路线

### P0：先完成“整篇输入基线”

- 仍用已经冻结的 12 道小样本和同一模型。
- 增加 `full_context` 变体：短论文全文输入；超过上下文预算时明确截断策略。
- 与 V0/V1 比较答案、输入 Token、延迟、引用定位，不把旧关键词命中当唯一裁判。

### P1：将证据变成一等数据结构

- 数据模型至少包含：`claim_id, answer_sentence, chunk_id, paper_id, page, quote, verification_status`。
- 生成前先提取 quote，生成后按 claim 做一次全新上下文核验。
- 页码、chunk_id、引用 ID 做确定性校验；语义支持才交给 LLM。

### P2：改进 RAG，而不是换 GraphRAG

- 向量召回形成较大的候选池。
- 加 BM25/关键词召回覆盖专名和数字。
- 使用轻量 reranker 或 query-focused contextual summary 重排。
- 对多论文限制每篇进入上下文的块数，避免单篇垄断证据预算。

### P3：形成真实科研工作流

- 接入 Zotero 集合/条目/附件，引用可跳回页码，结论可写回笔记。
- 增加“论文内问答 / 通用知识 / 跨论文综述”三种显式模式。
- 跨论文综述才启用 Planner -> Evidence Collector -> Synthesizer；Verifier 针对 claim，不承担开放式写作。

### P4：最后再试 GraphRAG

- 只选一个可证明价值的问题，例如“9 篇时间序列论文中模型组件、数据集和评价指标的关系与演化”。
- 与普通混合检索在同一组全局问题上比较覆盖率、成本和构图时间。
- 若没有明显收益，保留轻量 citation/evidence graph，不把 GraphRAG 塞进主链路。

## 最适合写进简历的升级故事

“最初实现向量 RAG 后，通过 72 题评测发现复杂路由和更细切块并不必然提升关键证据召回；随后设计整篇上下文/RAG 自适应策略，并参考 PaperQA2 和 Scholar QA 引入候选重排、quote-first 生成及 claim-证据核验，把系统从 ChatPDF 原型升级为可审计的科研阅读工作台。”
