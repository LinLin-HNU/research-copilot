## 用通俗的话理解新增工具

朴素基线就像一个普通开卷答题者：把书按固定长度裁开，每题找到意思最接近的几段，交给模型回答。
现有 V1 则会先判断题型，再找材料，尽量减少重复，并用章节结构补上遗漏，要求模型区分论文事实和自己的推断。
两者考同样的题，才能看复杂设计是否值得。但同时改了很多环节，只能比较整体系统，不能把全部提升归功于某一个模块。

盲评表相当于把两位答题者的名字遮住，随机排列答案再打分。它隐藏版本标签，文风仍可能让人猜出来，所以是尽力降低偏差，不是绝对看不出来。
置信区间是在提醒：“只考了这些题，真实水平可能还在较宽范围内。”同一论文出的题会相关，Wilson 区间只是简单近似，不是跨领域保证。
哈希是文件指纹。以后代码或题库变了，指纹会变，就不该拿旧数字当新版本结论。

## 你现在只需做的评测工作

先打开 `benchmark/experiments/private/audit_verified/gold_annotation.csv`。
前六列已有题目、题型、关键词和候选原文/页码。后面的 reference_key_points、verified_citations、reviewer、approved 留空给你核对。
候选摘录来自本地论文已有块，自动按关键词寻找；它们可能不够完整，必须对照 PDF，不能直接当 gold。

建议先核对前两道题，填好必须答出的要点，再把它们放入 dev_cases.json 的 gold。不要看了模型答案后才反过来决定标准。
之后生成两组答案，填 review.csv 的四项二元评分。找得到同学就抽一部分独立双评；找不到也可以自己评，但要诚实说明单人评阅。

现有 30 题已经用过，全部划为 dev。现在没有 10 篇/100 题，也没有 70 道冻结测试题。后续补材料时，先定参考答案、按论文留出测试，再冻结；不必为凑一个简历数字赶做低质量题。

本次没有替你自动打人工分，也没有调用另一个模型冒充人工。模拟测试中的 token 11/7 和 Synthetic 答案完全是测试夹具，不得写入简历指标。

## Docker：做了哪些准备，还卡在哪里

本机检查得到 CPU 为 Intel Core i5-12500H，VirtualizationFirmwareEnabled=False；Docker CLI 29.8.0 可用，但 desktop-linux 引擎管道不存在。
需要你保存工作，重启进入 UEFI/BIOS，启用 Intel Virtualization Technology/VT-x，保存退出。任务管理器 → 性能 → CPU 确认“虚拟化：已启用”。
然后完成 WSL 安装/更新并重启 Docker Desktop。Docker 的 WSL 2 后端要求硬件虚拟化开启，见 [官方 Windows 安装要求](https://docs.docker.com/desktop/setup/install/windows-install/)。

我补了 langchain-openai==1.3.3，版本与现有完整环境一致。LangChain 的 OpenAI 兼容模型集成需要此独立包，见 [官方 ChatOpenAI 集成文档](https://docs.langchain.com/oss/python/integrations/chat/openai)。这修复了一个依赖清单缺口，不等于已经验证干净镜像构建。

Docker 能正常启动后，在项目根目录运行：

```powershell
docker version
docker compose -f compose.local.yaml config --quiet
docker compose -f compose.local.yaml up --build -d
docker compose -f compose.local.yaml ps
docker compose -f compose.local.yaml logs --tail 100
```

然后访问 http://127.0.0.1:8000 。`compose.local.yaml` 是独立文件，不要和旧 compose.yaml 叠加，否则端口规则可能合并。
本机配置绑定 127.0.0.1，保留 resources 挂载，并增加首页健康检查。健康检查只能说明 Web 首页可访问，不能证明模型/OSS 可用。
完成后还要用真实 PDF 验证上传、摘要、追问、刷新历史，以及容器重建后的数据保留。

## 真正公网部署之前

本次只做部署准备，没有部署云服务器。当前代码还存在以下明确问题：

1. `/oss/token`、`/history`、`/chat/{thread_id}/messages`、删除历史接口都没有身份与资源归属验证。只保护一个 token 接口不够。
2. STS AssumeRole 未在请求中设置按用户目录收窄的 Policy。实际权限还取决于云端角色策略，本次没有访问云账号，不能假定它是宽权限或已安全。
3. `/chat` 的 PDF URL 由客户端传入，服务器直接下载；公网前应限定可信 OSS 来源、大小/超时，并处理重定向与内网地址访问风险。
4. 缺少请求限流、费用预算、并发限制，公开接口可能持续触发模型费用。
5. 还没有服务器、域名、HTTPS 反向代理及备份恢复验证。

面试演示可先采用“单用户、受密码保护的演示站”：整站网关认证，后端端口不直接暴露，限制上传和调用频率，使用专用低权限 OSS 角色/目录。它不等于多用户 SaaS，所有会话共享的限制要讲清楚。
若要支持多人使用，就需要真正的用户登录、逐个会话授权和用户隔离，不能只加一个共享密码便宣称完成。
服务器通常可用 Linux ECS/VPS 跑 Docker Engine，本机 Windows 虚拟化不是远程部署的前提；但需你提供目标服务器与演示访问方式，再完成配置和验收。
生产配置应与本机配置分开维护，见 [Docker Compose 生产部署指南](https://docs.docker.com/compose/how-tos/production/)。

## 面试时可以怎么讲

“我做的是一个单篇论文的证据约束阅读助手。上传 PDF 后先解析章节和页码，按会话存入向量库。问答时先区分论文事实、论文局限、通用知识和创新推理；需要论文的题才检索，通用知识不伪装成论文结论。”

“为了避免大段检索原文在每轮历史里重复发送，我把证据放到当轮动态系统提示里，不存成历史消息。普通问答仍会留在历史，所以我不说总 token 永远恒定，只说避免了检索原文的重复累积。”

“检索不仅看相似度，还用 MMR 减少重复，并用章节结构补材料。我发现找对章节不代表找到了关键实体，这让我把评测拆成路由、检索、最终答案三层。”

“目前有 3 篇论文 30 题的开发评测；最近一次历史过程指标是路由 30/30、检索 22/24。我知道样本小，所以补了置信区间，并且正在用同题朴素 RAG 对照和人工盲评验证最终答案。还没有验证过的提升我不会报数。”
