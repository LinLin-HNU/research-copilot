# 分支合并与运行目录：给自己看

## 分支不是三个复制的Git仓库

Git把每次提交保存为版本快照（通常复用不变内容）；分支是指向某次提交的名字。早期experiment从main同一提交分叉，后来只在experiment提交新代码，main就停在旧位置。worktree让同一个Git仓库的不同分支分别检出到两个文件夹，避免自己频繁切换目录内容。

|main|今后主要开发和GitHub默认入口|已通过4c91c70合并新版；后续文档提交继续推进|
|experiment/ablation-20261005|这轮独立实验与开发历史|deb3f99；已合并，先留着，不继续双线开发|
|release/v1-freeze-20261002|旧V1历史回退点|bfbec53；不合并新代码、不移动|

## 合并做了什么

先在experiment保存前端/Docker等未提交源码；主分支先保存复盘；原config模型选择改动单独stash保留，再在主项目main运行：

```powershell
git merge --no-ff experiment/ablation-20261005 -m 'merge: promote bounded research reading workflow to main'
```

Git以共同祖先为基准合并两边改动，生成有两个父提交的合并节点，而不是把两个目录简单覆盖复制。文档此次自动合并成功，没有手动删用户内容。

## 两套接口实际在哪里

合并后main中是一份app.py、一个FastAPI服务，同时含旧入口和新版入口：根页/及/chat保留旧V1使用方式；/research和/research/adaptive用于新版；/research/import导入本机PDF；/admin/research及其Trace API用于管理员观察。它们是同一服务的不同路由，不是每个Git分支对应一个HTTP接口。

旧入口是兼容路径，不等于源码完全冻结在旧版本：共同配置等可能已统一。要找完全旧代码应看release分支。未来维护新版为主，保留旧入口用于过渡，不再分别增加两套功能。

当前main代码在Research_Copilot；实验代码目录Research_Copilot_ablation仍保留。Git合并只处理受追踪源码，不转移.env、PDF、SQLite、Chroma、Trace等忽略文件。

当前8020 Docker使用实验目录的resources和docker_acceptance_runtime；容器运行镜像里的源码，不依赖PyCharm是否运行。Git合并/提交不会自动更新容器镜像。不要在main目录用同项目名直接up替换现有容器，因为相对挂载路径会换成main数据。

今后在main做新源码开发；本地演示先继续使用已经验收的实验目录Docker。若统一运行目录，另做停写→备份→数据及.env核对迁移→重新构建→验收，不能把“Git合并成功”当作迁移完成。实验目录暂不删除，里面仍有私有评测和演示数据。

旧config.py单行模型选择改动保存在stash提交544ce8371ec1fa1da9655114ecfb862171aadd2f。不要盲目stash pop覆盖统一模型工厂；需要该选择时应在当前.env设置对应服务商/模型，再小额验证。stash是本地备份，不会被git push上传。

## 回退不是git reset --hard

先明确回退代码还是数据。旧代码可在新目录检出冻结分支用于验证；当前main回滚优先新建可审计的revert提交或从固定版本另建修复分支。若撤销merge需明确主线父提交（如revert -m 1）及后续再次合并的影响，不随便执行。代码回退不会自动回滚已修改的数据库；数据恢复必须依靠备份。这些回退操作本次均未执行。
